1. O sistema

1.1 O que é

PokéDraft é um sistema web de entretenimento que simula uma batalha Pokémon entre duas pessoas. Diferente de um jogo tradicional, o jogador não escolhe livremente qualquer Pokémon: ele precisa montar um time dentro de um orçamento, a partir de um conjunto de Pokémon sorteado aleatoriamente e compartilhado com o adversário. Isso cria disputa: se você não pegar um Pokémon forte, o oponente pega.

Público-alvo: qualquer pessoa que goste de Pokémon, batalhas e um componente de sorte/estratégia.

1.2 Glossário do domínio

Termos que aparecem o tempo todo no código. Todo mundo do grupo precisa usar as mesmas palavras.

ConfrontoUm duelo 1×1 dentro da batalha simulada. Uma batalha tem vários confrontos.

1.3 As regras do jogo, em detalhe

a) Draft de Pokémon

  • O sistema sorteia vários samples de Pokémon (quantidade e tamanho definidos na Configuracao).
  • Os dois jogadores veem os mesmos samples — o que um pegar, o outro não pega mais.
  • Cada jogador pode banir Pokémon (limite definido em BansPorJogador). Pokémon banido sai de jogo para os dois.
  • Cada jogador pode comprar Pokémon, gastando pontos do seu budget.
  • Quando os pontos acabam, o jogador não pode comprar mais — a menos que venda alguém.
  • Venda: devolve um Pokémon do time e recupera Custo × FatorVenda pontos (sempre menos do que pagou).

b) Draft de itens

  • Existe um único sample de itens por partida (não vários, como nos Pokémon), também compartilhado.
  • Cada item pode ser equipado em um Pokémon do time, somando BonusOverall ao overall dele.
  • Um Pokémon carrega no máximo um item (campo ItemId em EscolhaPokemon, que é opcional).

c) Cálculo do overall

O overall tem duas partes:

ParteEntra no cálculoOnde fica guardado
Overall base
calculado no fim do draft		 Status base do Pokémon + bônus do item equipado + natureza + IVs EscolhaPokemon.OverallBase
Overall de confronto
calculado na hora da batalha		 Overall base + extras por: vantagem de tipagem contra o adversário daquele duelo, velocidade e tipo de ataque ConfrontoBatalha.OverallA e OverallB
Por que separar os dois? Porque o overall base é fixo (não depende do oponente), mas a vantagem de tipagem só existe contra um adversário específico. O mesmo Pokémon pode ter overall de confronto diferente dependendo de quem ele enfrenta.

d) Simulação da batalha

  1. Antes de simular, cada jogador define a ordem do seu time (campo OrdemNaBatalha).
  2. Os times se enfrentam 1×1 na ordem: o 1º do jogador A contra o 1º do jogador B, o 2º contra o 2º, e assim por diante.
  3. Em cada confronto, calcula-se o overall de confronto dos dois lados. Quem tiver o maior, vence e ganha 1 ponto para o seu jogador.
  4. Ao final, quem tiver mais pontos vence a batalha.
  5. Empate (ex.: 3–3): vence quem tiver a maior média de overall do time.

e) O que fica fora do escopo

  • Mais de uma geração de Pokémon.
  • Draft de golpes (moveset) — os Pokémon não escolhem ataques.
  • Escolher IVs e Naturezas manualmente — o sistema sorteia.

1.4 Fluxo completo de uma partida

1. CRIAR PARTIDA Escolher os 2 jogadores + a configuração (regras) → cria 1 registro em Partidas com Status = "Configuracao" 2. SORTEAR OS POOLS Sortear N samples de Pokémon + o sample único de itens → cria vários registros em PokemonNoPool e ItensNoPool → Partida.Status vira "Draft" 3. DRAFT (repete até os dois times ficarem prontos) ├─ banir Pokémon → PokemonNoPool.Banido = true + MovimentacaoDraft ├─ comprar Pokémon → cria EscolhaPokemon, gasta pontos + MovimentacaoDraft ├─ vender Pokémon → EscolhaPokemon.Vendida = true, devolve pontos + MovimentacaoDraft └─ equipar item → EscolhaPokemon.ItemId = X + MovimentacaoDraft 4. ORDENAR O TIME Cada jogador define EscolhaPokemon.OrdemNaBatalha (1, 2, 3...) → Partida.Status vira "Batalha" 5. SIMULAR A BATALHA Para cada posição: calcula overall dos dois lados e decide o vencedor → cria 1 registro em ConfrontosBatalha por duelo → soma os pontos em Partida.PontosJogadorA / PontosJogadorB → define Partida.VencedorJogadorId (empate: desempata pela média do overall) → Partida.Status vira "Finalizada"

Repare que praticamente toda ação do jogador gera dois efeitos: muda o estado atual (ex.: cria a escolha) e registra a movimentação no histórico. Isso permite reconstruir o saldo de pontos e mostrar o log do draft na tela.

2. Arquitetura

2.1 Stack e por que cada escolha

CamadaTecnologiaPapel e justificativa
BackendC# · ASP.NET Core MVC · .NET 8 Roda no servidor. Guarda as regras do jogo (validação de saldo, sorteio, cálculo de overall). É o exigido pela disciplina. Versão 8 porque é LTS e é a usada nas aulas.
APIControllers REST retornando JSON Expõe os dados para o frontend via GET/POST/PUT/DELETE. É o padrão CRUD pedido no planejamento.
BancoSQLite + Entity Framework Core 8 O banco inteiro é um arquivo (pokedraft.db). Ninguém precisa instalar nem configurar servidor de banco — crítico num grupo de 4 máquinas diferentes. O EF Core traduz classes C# em tabelas.
FrontendHTML · CSS · JavaScript (fetch) Sem framework (React/Angular). Views em Razor (.cshtml) e o JS chama a nossa própria API.
DadosPokéAPI (pokeapi.co) API pública e gratuita com status, tipos e sprites. Vamos importar para o nosso banco (não consultar em tempo real, para a tela não depender da internet).
ApoioGit + GitHub · Trello Versionamento e quadro Kanban de tarefas.
Mudança em relação ao planejamento original: o documento previa MySQL. Trocamos por SQLite. Motivo: MySQL exigiria cada integrante instalar e configurar um servidor, criar usuário/senha e manter a connection string diferente em cada máquina — muita chance de "na minha máquina funciona". Com SQLite o banco é gerado por comando e é idêntico para todos. O código C# é praticamente o mesmo: se um dia quisermos trocar, muda-se o pacote e uma linha no Program.cs.

2.2 O padrão MVC

MVC divide o sistema em três responsabilidades. A analogia clássica é um restaurante:

PeçaAnalogiaNo nosso projeto
ModelA cozinha e os ingredientesAs classes em Models/Entities/ e o acesso ao banco em Data/. São os dados e as regras.
ControllerO garçomAs classes em Controllers/. Recebem a requisição, chamam o Model e devolvem a resposta (uma View ou um JSON).
ViewO prato servido na mesaOs arquivos .cshtml em Views/. O HTML que o usuário enxerga.
Regra prática: o Controller nunca monta HTML. A View nunca acessa o banco. E as regras do jogo (cálculo de overall, validação de saldo) não ficam espalhadas na View — ficam no backend.

2.3 Duas formas de ligar frontend e backend

AbordagemComo funcionaOnde usamos
View Razor
clássica		 O Controller já devolve o HTML pronto com return View(dados). Páginas simples e estáticas: a home, telas de listagem sem interação pesada.
API + JavaScript
dinâmica		 O Controller devolve JSON; o JavaScript no navegador chama com fetch() e monta/atualiza a tela sem recarregar a página. A tela do draft, que muda a cada ban/compra/venda sem recarregar. É o foco do projeto.

2.4 O caminho completo de uma requisição

Exemplo: o jogador clica em "Comprar" um Pokémon na tela do draft.

NAVEGADOR │ usuário clica no botão "Comprar" ▼ JavaScript (wwwroot/js/site.js) │ fetch("/api/draft/comprar", { method:"POST", headers:{...}, body: JSON }) ▼ ROTEAMENTO ASP.NET (configurado em Program.cs) │ descobre qual Controller e qual método atende essa URL + verbo ▼ CONTROLLER (Controllers/DraftController.cs) │ valida a entrada, aplica a regra (o jogador tem saldo? o Pokémon está livre?) ▼ DbContext (Data/PokeDraftDbContext.cs) │ _context.EscolhasPokemon.Add(...); _context.SaveChanges(); ▼ EF CORE │ traduz o objeto C# em comandos SQL ▼ SQLite (arquivo pokedraft.db) │ INSERT INTO EscolhasPokemon (...) → grava ▲ │ ... e o caminho volta: CONTROLLER devolve return Ok(novoEstado) → vira JSON ▲ JavaScript recebe o JSON e atualiza a tela (saldo, lista, time)

Entender esse caminho é o que permite debugar: quando algo não funciona, você consegue perguntar "parou em qual etapa?" — o clique disparou? o fetch saiu? a rota bateu? o controller rodou? o banco gravou?

4.1 Arquivos da raiz

PokeDraft.sln

O que é: o arquivo de solução. Uma solução é apenas uma lista de projetos que formam o sistema.

Por que existe: hoje temos um único projeto (PokeDraft.Web), mas se um dia criarmos outro (ex.: um projeto separado só para os testes, ou um console para o importador da PokéAPI), ele é adicionado aqui e todos passam a compilar juntos com um dotnet build na raiz.

Você edita? Não à mão. Use dotnet sln add caminho/do/projeto.csproj.

global.json

O que é: trava a versão do SDK do .NET usada no projeto.

{ "sdk": { "version": "8.0.424", "rollForward": "latestFeature" } }

Por que existe: várias máquinas do grupo podem ter versões diferentes do .NET instaladas. Sem esse arquivo, um PC com .NET 10 compilaria com regras diferentes de um PC com .NET 8, gerando bugs que só acontecem "na máquina de fulano". Com ele, todo mundo usa o mesmo SDK.

O rollForward: permite usar uma versão 8.0.x mais nova se a exata (8.0.424) não estiver instalada — mas nunca pular para o 9 ou 10.

README.md

O que é: o documento de apresentação do repositório. É o que o GitHub mostra automaticamente na página inicial do projeto.

O que contém: descrição do sistema, tabela de tecnologias, pré-requisitos, como rodar, estrutura de pastas, modelo de dados, fluxo de Git e cronograma.

Importante: o README precisa ser mantido atualizado — é o primeiro lugar que o professor vai olhar na entrega final.

.gitignore

O que é: a lista do que o Git deve ignorar.

O que ignoramos e por quê:

ItemMotivo

PokeDraft.Web/Program.cs

O que é: o ponto de entrada da aplicação. É a primeira coisa que roda. Divide-se em duas metades:

Metade 1 — registrar serviços (o que a aplicação sabe fazer):

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();   // habilita Controllers + Views (MVC)

// registra o nosso banco: EF Core usando SQLite,
// com a connection string que está no appsettings.json
builder.Services.AddDbContext<PokeDraftDbContext>(options =>
    options.UseSqlite(builder.Configuration.GetConnectionString("PokeDraftDb")));

Metade 2 — montar o pipeline (por onde cada requisição passa, na ordem):

var app = builder.Build();

app.UseHttpsRedirection();   // http → https
app.UseStaticFiles();        // serve o que está em wwwroot/
app.UseRouting();            // descobre qual controller atende a URL
app.UseAuthorization();      // checa permissões (ainda não usamos)

app.MapControllerRoute(      // a rota padrão do MVC
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();                   // sobe o servidor

A rota padrão explicada: {controller=Home}/{action=Index}/{id?} significa que a URL /Pokemon/Detalhes/25 chama o método Detalhes(25) da classe PokemonController. Se a URL for só /, usa os padrões: HomeController.Index(). O ? em id quer dizer opcional.

Você vai mexer aqui quando: registrar um novo serviço (ex.: o HttpClient do importador da PokéAPI) ou uma classe de regra de negócio.

4.5 Data — a ponte com o banco

Data/PokeDraftDbContext.cs

O que é: a classe mais importante da camada de dados. Herda de DbContext (do EF Core) e faz três coisas:

1. Declara as tabelas — um DbSet<T> por entidade:

public DbSet<Pokemon> Pokemons => Set<Pokemon>();
public DbSet<Item> Itens => Set<Item>();
public DbSet<Jogador> Jogadores => Set<Jogador>();
// ... e assim por diante, 10 no total

É por meio deles que se consulta e grava: _context.Pokemons.ToList(), _context.Jogadores.Add(j).

2. Configura o mapeamento no método OnModelCreating:

  • Enums como texto: .HasConversion<string>() faz o banco guardar "Draft" em vez de 2. Fica muito mais fácil de ler abrindo o banco direto.
  • Índices únicos: em Pokemon.PokeApiId (evita importar duplicado) e Configuracao.Nome.
  • Relacionamentos: quem aponta para quem e o que acontece ao apagar (ver seção 5.4).
  • Dado inicial: a configuração "Padrão" (ver 5.5).

3. Recebe as opções por injeção de dependência — o construtor recebe DbContextOptions, que o Program.cs preencheu com "use SQLite, arquivo pokedraft.db".

Quando você mexe neste arquivo: sempre que criar uma entidade nova (adicionar o DbSet) ou precisar configurar um relacionamento/índice. Depois de mexer, gere uma migration.

Uma migration é um "commit do formato do banco". Ela guarda, em código, exatamente quais tabelas/colunas criar ou alterar. É isso que permite os 4 integrantes terem bancos idênticos sem passar arquivo .db um para o outro.

5.1 Diagrama de relacionamentos

┌──────────────────────────────────────────────────────────────┐ │ CATÁLOGO — cadastrado uma vez, vale para todas as partidas │ │ │ │ Pokemon · Item · Jogador · Configuracao │ └──────────────────────────────────────────────────────────────┘ │ │ são referenciados por… ▼ ┌──────────────────────────────────────────────────────────────┐ │ PARTIDA │ │ a entidade central: aponta para Configuracao (regras), │ │ Jogador A, Jogador B e Jogador Vencedor │ └──────────────────────────────────────────────────────────────┘ │ │ …e tudo abaixo pertence a UMA partida ▼ PokemonNoPool ....... o sorteio dos Pokémon → Pokemon ItemNoPool .......... o sorteio dos itens → Item EscolhaPokemon ...... o time montado → Pokemon + Item + Jogador MovimentacaoDraft ... o histórico de ações → Jogador (+ Pokemon / Item) ConfrontoBatalha .... os duelos 1×1 → EscolhaPokemon (A e B)

Lendo o diagrama:

  • Catálogo (Pokemon, Item, Jogador, Configuracao): dados que existem independentemente de qualquer partida. Preenchidos uma vez (importador da PokéAPI, cadastro de jogadores).
  • Partida é o centro. Tudo que acontece durante o jogo pertence a uma partida.
  • As tabelas de jogo ligam o catálogo à partida: PokemonNoPool diz "este Pokémon do catálogo está no pool desta partida"; EscolhaPokemon diz "este Pokémon do catálogo está no time deste jogador nesta partida".
  • ConfrontoBatalha aponta para EscolhaPokemon (e não para Pokemon) porque o que luta é o Pokémon já montado, com item e IVs.

5.4 Regras de exclusão (o que acontece ao apagar)

Quando você apaga um registro, o que acontece com quem apontava para ele? Definimos isso explicitamente:

RelacionamentoComportamentoEfeito prático
Partida → PokemonNoPool, ItensNoPool,
EscolhasPokemon, MovimentacoesDraft,
ConfrontosBatalha		CascadeApagar uma partida apaga tudo que pertence a ela. Faz sentido: pool, time e histórico não existem fora da partida.
Pokemon / Item / Jogador /
Configuracao → qualquer coisa		RestrictO banco impede apagar um Pokémon, item, jogador ou configuração que esteja sendo usado em alguma partida. Evita deixar registros órfãos e apagar histórico sem querer.

Por que não deixar tudo em Cascade? Além de perigoso (um DELETE errado apagaria meia base), o EF/SQL não permite múltiplos caminhos de cascata chegando na mesma tabela. Como EscolhaPokemon depende tanto de Partida quanto de Jogador, se os dois fossem Cascade daria erro ao criar o banco. Escolhemos: Partida cascateia, os demais restringem.

6. Conceitos de C# e EF Core que aparecem no código

Tudo aqui está no código que já existe. Se algum trecho parecer estranho ao abrir um arquivo, provavelmente a explicação está nesta seção.

6.1 Propriedades com get; set;

public string Nome { get; set; } = null!;

Uma propriedade é um campo com controle de leitura (get) e escrita (set). O EF Core só transforma em coluna aquilo que for propriedade pública com get e set — por isso todas as entidades usam esse formato.

6.2 Nulos: ? e = null!

Como o projeto tem <Nullable>enable</>, o compilador diferencia o que pode ou não ser nulo:

EscritaSignificado
string NomeObrigatório. No banco vira coluna NOT NULL.
string? DescricaoOpcional. Pode ser nulo; coluna aceita NULL.
int? OrdemNaBatalhaNúmero que pode não ter valor ainda. Diferente de zero: null = "não definido", 0 = "definido como zero".
= null!Uma promessa ao compilador: "sei que parece nulo agora, mas o EF preenche antes de qualquer uso". Serve só para silenciar o aviso — não muda o banco.

6.3 Propriedades de navegação e ICollection

public int PartidaId { get; set; }              // vira coluna (a FK)
public Partida Partida { get; set; } = null!;   // navegação: NÃO vira coluna

public ICollection<EscolhaPokemon> Escolhas { get; set; } = new List<EscolhaPokemon>();

O par PartidaId + Partida é a convenção do EF: o int é a chave estrangeira real; o objeto é o atalho para navegar no C#. A coleção é o lado "muitos" do relacionamento — permite escrever partida.Escolhas em vez de fazer outra consulta.

Para a navegação vir preenchida do banco, é preciso pedir com Include:

var partida = _context.Partidas
    .Include(p => p.Escolhas)
        .ThenInclude(e => e.Pokemon)
    .FirstOrDefault(p => p.Id == id);

Sem o Include, partida.Escolhas vem vazia — não é bug, é o EF evitando carregar dados que você não pediu.

6.4 Enums e HasConversion<string>()

Por padrão o EF guardaria StatusPartida.Draft como o número 2. Configuramos para guardar o texto "Draft":

modelBuilder.Entity<Partida>()
    .Property(p => p.Status).HasConversion<string>().HasMaxLength(20);

Custa alguns bytes a mais, mas quem abrir o banco lê "Finalizada" em vez de decifrar 4. Para um projeto de estudo, vale muito.

6.5 Data Annotations vs Fluent API

Duas formas de configurar o mapeamento. Usamos as duas:

FormaOndeUsamos para
Data AnnotationAtributo em cima da propriedade, na entidade: [MaxLength(60)]Coisas simples e locais: tamanho máximo de texto.
Fluent APIMétodo OnModelCreating, no DbContextCoisas que envolvem mais de uma entidade: relacionamentos, comportamento de exclusão, índices compostos, conversões, seed.

6.6 Injeção de dependência

public class PokemonController : ControllerBase
{
    private readonly PokeDraftDbContext _context;

    public PokemonController(PokeDraftDbContext context)   // chega pronto
    {
        _context = context;
    }
}

Você nunca escreve new PokeDraftDbContext(...) num controller. Como o Program.cs registrou o DbContext com AddDbContext, o ASP.NET cria e entrega a instância no construtor automaticamente — e cuida de fechar a conexão no fim da requisição. Mesmo padrão do ILogger no HomeController.

6.7 LINQ — consultando o banco

var disponiveis = _context.PokemonNoPool
    .Where(p => p.PartidaId == partidaId
             && !p.Banido
             && p.CompradoPorJogadorId == null)
    .Include(p => p.Pokemon)
    .OrderBy(p => p.NumeroSample)
    .ToList();

O EF traduz isso em SELECT ... WHERE ... ORDER BY. A consulta só é executada quando você chama ToList(), FirstOrDefault() ou similar.

MétodoO que faz
.Where(...)Filtra (vira WHERE).
.OrderBy / .OrderByDescendingOrdena.
.Include(...)Traz junto os dados relacionados.
.FirstOrDefault(...)Pega o primeiro ou null se não achar.
.Any(...) / .Count(...)Existe algum? Quantos?
.ToList()Executa e traz os resultados.

6.8 Gravando: SaveChanges

_context.Jogadores.Add(novoJogador);
_context.SaveChanges();     // só aqui o banco é realmente alterado

O DbContext acumula as mudanças em memória e grava tudo de uma vez no SaveChanges(), dentro de uma transação. Se der erro no meio, nada é gravado — importante para operações como "comprar Pokémon", que mexem em três tabelas ao mesmo tempo.

6.9 async / await

public async Task<IActionResult> Listar()
{
    var lista = await _context.Pokemons.ToListAsync();
    return Ok(lista);
}

Versões assíncronas liberam a thread enquanto o banco responde, permitindo o servidor atender mais requisições. Regra: se o método tem await, ele precisa ser async e devolver Task<...>. Vamos usar async nos controllers de API e no importador da PokéAPI.

7. Receita: criando uma funcionalidade do zero

Exemplo real e completo: CRUD de Jogador (parte da entrega de 11/09). Os mesmos seis passos servem para qualquer entidade.

Passo 1 — A entidade já existe?

Models/Entities/Jogador.cs já existe e já está no DbContext como DbSet<Jogador> Jogadores. Se fosse uma entidade nova, seria preciso criar a classe, adicionar o DbSet e gerar uma migration:

Passo 2 — O Controller de API

Criar Controllers/JogadorController.cs:

using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using PokeDraft.Web.Data;
using PokeDraft.Web.Models.Entities;

namespace PokeDraft.Web.Controllers;

[ApiController]                        // marca como controller de API
[Route("api/[controller]")]            // rota base: /api/jogador
public class JogadorController : ControllerBase
{
    private readonly PokeDraftDbContext _context;

    public JogadorController(PokeDraftDbContext context) => _context = context;

    [HttpGet]                                          // GET /api/jogador
    public async Task<IActionResult> Listar()
        => Ok(await _context.Jogadores.OrderBy(j => j.Nome).ToListAsync());

    [HttpGet("{id}")]                                  // GET /api/jogador/3
    public async Task<IActionResult> Obter(int id)
    {
        var jogador = await _context.Jogadores.FindAsync(id);
        if (jogador is null) return NotFound();
        return Ok(jogador);
    }

    [HttpPost]                                         // POST /api/jogador
    public async Task<IActionResult> Criar(Jogador jogador)
    {
        if (string.IsNullOrWhiteSpace(jogador.Nome))
            return BadRequest("O nome é obrigatório.");

        _context.Jogadores.Add(jogador);
        await _context.SaveChangesAsync();
        return CreatedAtAction(nameof(Obter), new { id = jogador.Id }, jogador);
    }

    [HttpPut("{id}")]                                  // PUT /api/jogador/3
    public async Task<IActionResult> Atualizar(int id, Jogador dados)
    {
        var jogador = await _context.Jogadores.FindAsync(id);
        if (jogador is null) return NotFound();

        jogador.Nome = dados.Nome;
        await _context.SaveChangesAsync();
        return Ok(jogador);
    }

    [HttpDelete("{id}")]                               // DELETE /api/jogador/3
    public async Task<IActionResult> Remover(int id)
    {
        var jogador = await _context.Jogadores.FindAsync(id);
        if (jogador is null) return NotFound();

        _context.Jogadores.Remove(jogador);
        await _context.SaveChangesAsync();
        return NoContent();
    }
}
RetornoCódigo HTTP e quando usar
Ok(dados)200 — deu certo, aqui está o resultado.
CreatedAtAction(...)201 — criado com sucesso.
NoContent()204 — deu certo, não há nada para devolver (típico do DELETE).
BadRequest("msg")400 — o cliente mandou algo inválido.
NotFound()404 — o id não existe.

Passo 5 — O JavaScript

Criar wwwroot/js/jogadores.js:

async function carregarJogadores() {
    const resposta = await fetch("/api/jogador");
    if (!resposta.ok) {                        // sempre trate o erro
        alert("Erro ao carregar jogadores.");
        return;
    }
    const jogadores = await resposta.json();

    const lista = document.getElementById("lista");
    lista.innerHTML = "";
    jogadores.forEach(j => {
        lista.innerHTML += `<li>${j.nome}
            <button onclick="removerJogador(${j.id})">x</button></li>`;
    });
}

async function criarJogador() {
    const nome = document.getElementById("nome").value;

    const resposta = await fetch("/api/jogador", {
        method: "POST",
        headers: { "Content-Type": "application/json" },   // obrigatório!
        body: JSON.stringify({ nome })
    });

    if (!resposta.ok) { alert("Não foi possível criar."); return; }

    document.getElementById("nome").value = "";
    carregarJogadores();                        // atualiza a lista
}

async function removerJogador(id) {
    await fetch(`/api/jogador/${id}`, { method: "DELETE" });
    carregarJogadores();
}

carregarJogadores();                            // roda ao abrir a página
Atenção ao nome dos campos no JSON. No C# a propriedade é Nome (maiúscula), mas o ASP.NET converte para nome (minúscula) no JSON por padrão. No JavaScript use j.nome, não j.Nome.

9. Fluxo de trabalho: Git e Trello

9.1 O ciclo de uma tarefa

1. Pega um card no Trello e move para "Em desenvolvimento" 2. git pull ← sempre comece atualizado 3. git checkout -b feat/nome-da-tarefa ← branch própria 4. ... programa ... 5. dotnet build ← tem que passar 6. git add . && git commit -m "mensagem clara" 7. git push -u origin feat/nome-da-tarefa 8. Abre Pull Request no GitHub; um colega revisa e aprova 9. Merge na main → move o card para "Concluído"

9.2 Regras combinadas

  • A main tem que sempre compilar e rodar. Ninguém commita direto nela.
  • Uma tarefa = um branch = um Pull Request. Branches curtos evitam conflitos gigantes.
  • Prefixos de branch: feat/ (funcionalidade nova), fix/ (correção), docs/ (documentação).
  • Deu git pull e veio migration nova? Rode dotnet ef database update.
  • Vai criar uma migration? Avise no grupo antes (ver o alerta na seção 4.6).
  • Nunca commite bin/, obj/ ou pokedraft.db — o .gitignore já cuida disso.
